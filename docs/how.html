The Machinery

How a compiler written in Python comes to run in a web browser, what really happens when you press Run, and what it costs.

The short answer

The EnglishScript compiler is ordinary Python: a few thousand lines of it, with no dependencies. A browser cannot run Python. It can run WebAssembly, and the Python interpreter itself has been compiled to WebAssembly by a project called Pyodide. So the page downloads a Python interpreter, hands it the compiler's files, and calls it.

One thing is easy to get wrong, so it is worth saying plainly. Nothing here translates Python into WebAssembly. The interpreter, which is written in C, is what was compiled. It then reads the compiler's Python files exactly as they are in the repository, byte for byte, and runs them the way Python on your own computer would.

The same is true one level up. Your EnglishScript program is not turned into WebAssembly either. The compiler turns each sentence into a small Python function, and the interpreter runs those.

The layers

What happens when you press Run

The page does nothing with Python until you ask it to. The first press of Run, or the first visit to the playground, sets this off:

  1. The interpreter is fetched. A small script, pyodide.js, is loaded from a public file server. It fetches the interpreter (pyodide.asm.wasm) and Python's standard library, and the browser compiles the WebAssembly into the machine code of your computer.
  2. The compiler is fetched. The page downloads play/englishscript.zip, which holds the Python files of the englishscript package.
  3. The files are unpacked into a pretend disk. The interpreter has a file system that exists only in the tab's memory. The zip is unpacked there, and that folder is put on Python's search path, so import englishscript works as it does anywhere.
  4. A short bridge is defined. The page runs a few dozen lines of Python that define two functions, play and check. They call the compiler and give their results back as text in the JSON format, which both languages read easily.
  5. Your program is passed in. JavaScript calls play with the text of your program. Python compiles it, runs it, and returns a list of what happened: each line said, each question asked, or the compiler's refusal.
  6. The page writes it out. JavaScript turns that list into elements of the page.

Steps one to four happen once. After that, pressing Run is only steps five and six, which is why the second run feels instant.

The heart of it is short. This is from docs/play/engine.js, trimmed a little:

const py = await loadPyodide({ indexURL: PYODIDE });
const response = await fetch("play/englishscript.zip");
py.FS.mkdirTree("/site");
py.unpackArchive(await response.arrayBuffer(), "zip", { extractDir: "/site" });
py.runPython(BRIDGE);                  // defines play() and check() in Python
const play = py.globals.get("play");   // a Python function, callable from JavaScript

const result = JSON.parse(play(source, "run", JSON.stringify(replies)));

What “compile” means here

The word is used loosely on this site, so here is exactly what the compiler does to a program. There are two stages, both in Python.

The lexer splits the text into sentences, one to a line, and each sentence into words, numbers, quoted text and punctuation. It also works out which sentences are indented under which.

The compiler then goes through the sentences once, in order. For each one it does three things together: it works out which of the sentence forms this is, it checks that every word has exactly one meaning at that point, and it builds a Python function that will carry the sentence out. A sentence such as

Add 5 to the total.

becomes, in effect, this:

lambda env: env.set("total", env.get("total") + 5)

No sentence is carried out until every sentence has been through this, which is why a mistake on the last line is reported before the first line runs. Running the program is then nothing more than calling those functions in order.

So there is no bytecode of EnglishScript's own, and no WebAssembly is made from your program. A stricter name for the compiler would be a checker that builds closures. What makes it deserve the word is the checking: it settles every name, every pronoun and every type before anything happens.

Questions, without stopping the page

The to-do list asks for commands. At a terminal that is easy: the program stops and waits for a line. A web page cannot do that. Python here runs on the page's one and only thread, and a program that sat waiting would freeze the whole tab, input box included.

The page gets round this with a trick that only works because EnglishScript programs are predictable. When a program asks a question that nobody has answered yet, it is stopped, and the page shows what it said so far with an input box. When you answer, the program is run again from the top, this time with your answer supplied. Ask a second question and it runs a third time, with both answers.

Because a program has no clock and no chance in it, every run says the same things up to the point where the new answer is used. You see one continuous conversation. The cost is that an interactive program gets a little slower with each answer, which only matters for the heaviest example.

Files that are not really files

When the to-do list writes todo.txt, it writes to that pretend disk in the tab's memory. The page copies the files a program leaves behind and puts them back before the next run, so the list is still there when you run the program again. It is gone when you reload the page. Nothing is written to your computer and nothing is sent anywhere.

Checking as you write

The playground underlines mistakes while you type. A third of a second after you stop, it passes the whole program to check, which compiles it without running it and returns every problem with its line and its place in the line. The page draws the underlines on a layer beneath the text box, so that they sit exactly under the letters.

What it costs

These were measured in one browser on one computer. The sizes are of the files once unpacked; they travel compressed.

What is fetchedSize
The Python interpreter, as WebAssembly9.9 MB
Python's standard library2.3 MB
The script that starts the interpreter1.2 MB
The EnglishScript compilerabout 130 KB
  • The first run is slow to start. Nearly all of the download is the interpreter, and the compiler is about one per cent of it. While it arrives, the page shows how much has come. The browser keeps a copy, so later visits start much sooner.
  • It runs somewhat slower than on your own machine. Setting up the SHA-256 example took 0.7 seconds here and 0.4 with ordinary Python on the same computer.
  • A long-running program freezes the tab until it finishes, because it shares the page's thread. A While loop is stopped after a million rounds, which catches the usual accident.
  • Some things are out of reach. A browser has no way to call a graphics driver, so the vulkan library reports that it cannot start.
  • The page depends on two outside addresses: one for the interpreter and one for the typefaces. Without the first, the text and the printed outputs can still be read, but nothing runs.

How the page is kept honest

A page like this could easily show outputs that the compiler no longer gives. Three things prevent it.

  • The compiler is not a copy. A script, tools/build_site.py, zips the package from the repository. A test fails if the zip and the source differ.
  • The printed outputs are produced, not typed. The same script runs every program printed in the treatise and writes what the compiler says into the page.
  • The grammar is run. Every example in the grammar is run by the test suite, and that page is printed from the same document the tests read.

What a real compiler to WebAssembly would take

Everything above carries an interpreter around in order to run a program. The alternative is to translate an EnglishScript program directly into WebAssembly, or into JavaScript, so that the result runs on its own. The checking would stay as it is; only the last step, building the functions, would be replaced by writing out instructions.

That is not built. It would make programs start at once and run far faster, at the price of a second thing to keep in step with the first. For a language whose point is that it can be read, the slow and simple arrangement was the right one to begin with.
