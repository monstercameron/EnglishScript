Beside JavaScript and Java

The same programs in three languages, and what each language decides for you without saying so.

JavaScript and Java share four letters, a year of birth and a family of brackets, and not much else. One checks almost nothing before a program runs. The other checks the types and then takes your word for the rest. EnglishScript is far smaller and far slower than either, and nobody should build a product in it. It is set beside them here because they are the two languages most people meet first, and because the comparison shows plainly what strict English buys and what it costs.

One program, three times

A bank with two accounts and one rule: no account may go below nothing. Money is paid from one to the other, the rich are counted, a check is made, and a payment that would break the rule is tried and refused.

class Account {
  #cents;
  constructor(name, cents) {
    this.name = name;
    this.balance = cents;
  }
  get balance() { return this.#cents; }
  set balance(cents) {
    if (cents < 0) throw new RangeError("An account's balance is never less than $0.");
    this.#cents = cents;
  }
  get rich() { return this.balance >= 100_000; }
}

const ada = new Account("Ada", 120_000);
const bo = new Account("Bo", 4_000);
const accounts = [ada, bo];

function pay(cents, giver, taker) {
  giver.balance -= cents;
  taker.balance += cents;
}

const dollars = (cents) => "$" + (cents / 100).toLocaleString("en-US");

pay(30_000, ada, bo);
console.log(`${accounts.filter((account) => account.rich).length} rich.`);
console.log(`Ada has ${dollars(ada.balance)} and Bo has ${dollars(bo.balance)}.`);
console.assert(accounts.reduce((sum, account) => sum + account.balance, 0) === 124_000);

try {
  pay(50_000, bo, ada);
} catch (problem) {
  console.log(`Refused. ${problem.message}`);
}
import java.math.BigDecimal;
import java.util.List;

final class Account {
    final String name;
    private BigDecimal balance;

    Account(String name, String balance) {
        this.name = name;
        setBalance(new BigDecimal(balance));
    }

    BigDecimal balance() {
        return balance;
    }

    void setBalance(BigDecimal value) {
        if (value.signum() < 0) {
            throw new IllegalStateException("An account's balance is never less than $0.");
        }
        balance = value;
    }

    boolean isRich() {
        return balance.compareTo(new BigDecimal("1000")) >= 0;
    }
}

public class Bank {
    static void pay(BigDecimal amount, Account giver, Account taker) {
        giver.setBalance(giver.balance().subtract(amount));
        taker.setBalance(taker.balance().add(amount));
    }

    public static void main(String[] args) {
        var ada = new Account("Ada", "1200");
        var bo = new Account("Bo", "40");
        var accounts = List.of(ada, bo);

        pay(new BigDecimal("300"), ada, bo);
        System.out.println(accounts.stream().filter(Account::isRich).count() + " rich.");
        System.out.println("Ada has $" + ada.balance() + " and Bo has $" + bo.balance() + ".");

        var total = accounts.stream().map(Account::balance).reduce(BigDecimal.ZERO, BigDecimal::add);
        if (total.compareTo(new BigDecimal("1240")) != 0) {
            throw new AssertionError("The total is " + total);
        }

        try {
            pay(new BigDecimal("500"), bo, ada);
        } catch (IllegalStateException problem) {
            System.out.println("Refused. " + problem.getMessage());
        }
    }
}

The number of words is about the same in the first two. Sentences are not shorter than code. The difference is in the marks. EnglishScript's eleven are the brackets round each kind of value, such as (money), and the colons that open a block. Marks inside quotation marks were not counted in any of the three.

The English version also says five things that the other two leave to habit.

  • Money is a kind of value. $300 is money, and adding a plain number to it is refused. The JavaScript keeps cents in an ordinary number and writes its own function to print them. The Java builds a BigDecimal from text each time.
  • The rule is a sentence of its own. It is stated once and holds for every change, wherever the change is made. In the other two it lives inside a setter, and it holds for as long as every change remembers to go through the setter.
  • The roles are named. Pay $300 from Ada to Bo. says who gives and who receives. In pay(30_000, ada, bo) only the order says so, and swapping the last two is still a correct call in both languages. JavaScript goes further: pay(ada, 30_000, bo) runs without complaint and leaves Bo's balance as the text 4000[object Object]. Java refuses that one, because the types are wrong.
  • The check is part of the program. For example stops the program if it does not hold. JavaScript's console.assert only prints a message, and the Java has to throw by hand or bring in a testing library.
  • A failed attempt is undone. When something inside Try fails, every change made inside it is put back. In the other two, whatever pay did before it failed stays done unless the programmer writes the undoing.

Where they part company

Six small questions, put to all three. In each, JavaScript and Java have an answer fixed by a rule that the reader has to know. EnglishScript's answer is usually to refuse and ask.

JavaScript and Java beside each other

The two are often confused because of the name, which was a piece of marketing in 1995. They were made in the same year by different people for different jobs, and they have grown toward each other since without meeting.

The plainest difference between the two is when they find a mistake. Java finds a great many before the program runs, at the price of saying everything twice: once for the compiler and once for the reader. JavaScript finds them when the line is reached, or does not find them and produces NaN.

What EnglishScript takes from each

From Java, the habit of checking first. A property has a declared kind, a sentence that does not fit is refused before anything runs, and the refusal names the place. EnglishScript carries the habit into two places Java leaves alone: a value that may be missing, and a phrase that can be read two ways.

From JavaScript, the lack of ceremony. A program can be one line, there is nothing to declare before saying something, and it runs in a web page. The page written in English is the nearest thing here to what JavaScript was made for.

From neither, the sentence. Both of the others are written in a notation and read by people trained in it. EnglishScript is written in the reader's language, and spends its strictness on making sure that what the reader understands is what will happen.

What they can do that it cannot

  • Run fast. Either of them is many thousands of times quicker. EnglishScript turns each sentence into a Python function and counts in exact fractions.
  • Hold data in more shapes. They have arrays, maps and sets. EnglishScript has things with properties, and lists that can be added to, indexed and changed but not yet sorted. It has no maps and no sets.
  • Call on other people's work. Each has hundreds of thousands of published libraries. EnglishScript has two, both in its own repository.
  • Do several things at once. That part of EnglishScript is designed and not built.
  • Be debugged. They have steppers, profilers and editors that know the language. EnglishScript has a linter and a playground.
  • Grow large. Programs of a million lines exist in both. The largest EnglishScript program is a few hundred sentences long.

So this is not a contest, and the table above should not be read as one. JavaScript and Java are tools for building things. EnglishScript is an argument, with a working compiler attached, about one question they both answered early and never reopened: whether a program has to be written in a notation that its eventual readers cannot read. The treatise makes that argument at length.
