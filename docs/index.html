A Treatise, with a Compiler

EnglishScript

or, English made strict enough to compile

A programming language made of English sentences, and a compiler that accepts a sentence only if it has exactly one meaning. Herein the argument, the evidence, and the compiler itself, which runs upon this very page.

Try it now Open the playground The grammar The machinery

❦

The thesis

Programming in English works when ambiguity is a compile error.

English is easy to read because it leaves things unsaid. We say “its” and “the dragon” and “the treasures of the dragon” without spelling out which thing, which dragon or which link between them. That is safe exactly when the unsaid part can be recovered in one way only.

So the compiler's job is not to guess what a sentence means. Its job is to check that there is only one thing it could mean, and to refuse the sentence, with an explanation, when there is more than one. Three claims follow from that, and the rest of this page argues for them.

  1. Readable and strict are not opposites. A program can read as plain English and still mean exactly one thing.
  2. The refusal is the interface. A writer learns the language from what the compiler declines and why.
  3. A language model belongs in front of such a compiler, not in place of it.

Two ways this has failed before

Formal languages dressed as English. COBOL, HyperTalk and AppleScript were designed to read like English, and they do. Writing them is another matter. The parser accepts a narrow set of phrasings, and the English look of the language promises a freedom it does not have. You are left guessing which English it wants.

Prompts to a language model. Here any English is accepted, which is the opposite failure. The same request can produce different programs on different days, and nothing tells you when the model has guessed. This project began that way, in 2023, as a notebook that asked a language model to turn sentences into JavaScript under a list of written rules. The model ignored the rules and wrote sensible JavaScript anyway. The rules meant nothing, because nothing enforced them.

Implicit is not the same as ambiguous

The word “its” is implicit. It does not name the thing it belongs to. Inside a loop over dragons there is only one thing it could belong to, so it is allowed.

Put a second loop inside the first and the same word becomes ambiguous. A person would probably guess the nearer thing. The compiler does not guess.

That message is the second claim in practice. It names the two readings and shows the sentence that removes the doubt. The language is learned from messages like it.

The rules that make English strict

Each rule takes a habit of ordinary English and adds the condition under which it has one meaning.

A glossary comes first

English depends on shared vocabulary. Here the vocabulary is written down: every kind of thing, adjective and verb is defined before it is used, as in the definitions section of a contract. A word that has not been defined is refused, and the message shows how to define it.

“Of” must mean one thing

“The treasures of Smaug” works because a treasure is tied to a dragon in exactly one way, through its owner. When there are two ways, the phrase is refused until the program says which.

Prepositions name a verb's roles

English already has named arguments: “send the knight against the dragon”. A verb is taught with its prepositions and the kind of thing each one takes. Every role is then checked wherever the verb is used.

Brackets carry the type, and units do not mix

Whatever is not obvious from a name goes in brackets after it: (money), (number), (horse, if any). Money, plain numbers and percentages are different things, as they are in speech. Nobody adds “five” to “three hundred dollars” without saying five what.

“And” with “or” needs brackets

Most programming languages settle this with a rule of precedence that the reader has to remember. English has no such rule, so the sentence is refused until brackets show which reading is meant.

What may be missing must be checked

A knight may have no horse. Writing (horse, if any) says so, and from then on the compiler will not let the horse be used until the program has checked that it is there.

“Never” and “for example” are part of the language

A sentence with “never” or “always” is a rule, checked every time the thing changes. A sentence starting “For example” is a test that runs with the program. Both are things people write anyway, in comments and in separate test files.

The evidence

A language is tested by what can be written in it. Three programs were written to push this one, and each is in the repository.

A to-do list

An ordinary small application: it asks for commands, makes and removes tasks, marks them done, and keeps the list in a file between runs. It is in the playground above. Its first run has no saved file, and it handles that with a sentence most people could read aloud: Try: to load the list, and If that fails: to start a new one.

SHA-256, from first principles

EnglishScript has no bit operators, no remainders and no arrays. This program builds them. A number's lowest bit is whether it is divisible by two, halving it shifts every bit one place to the right, and an array is a kind of thing with a place and a value. The algorithm's 72 constants are not typed in: the program finds the first 64 primes and takes their cube and square roots by bisection on whole numbers about 105 bits long.

It gives the same answers as Python's own hashlib, including for messages several blocks long. It is also slow, at about 300 bytes a second. It is in the playground too.

A triangle on a graphics card

A program can say Use the vulkan library. and then draw with sentences such as Draw Hello on Canvas. Each sentence stands for a handful of calls to the real Vulkan API. This picture was drawn that way by an ordinary graphics card and read back:

The reference is tested

Every example in the grammar is run by the test suite, and so is every example on this page. If the compiler changes and the documents do not, a test fails.

❦

What it costs

  • You still have to learn which sentences are accepted. This is the old weakness of English-like languages, and it is not gone. The error messages are the defence against it, and whether they are enough is an open question that only people who did not write the compiler can answer.
  • Arithmetic reads worse in words. For this reason sums are written in symbols, as English writing has done for centuries.
  • It is slow. Each sentence becomes a Python closure and numbers are exact fractions. That suits bookkeeping and teaching, and it does not suit heavy computation.
  • It is not finished. Lists are only partly there. Dates, units, picking from a group and doing things at the same time have a designed syntax and no implementation.
  • Strictness is sometimes tedious. In a nested loop the compiler makes you write “the treasure's worth” where a person would have understood “its worth”.

Where a language model belongs

The first column of the table above is still “No”. EnglishScript does not accept loose English, and a parser never will.

A language model can. The arrangement this thesis points to has two steps. A model rewrites what you said into strict sentences like the ones on this page. The compiler then accepts the result or refuses it and says why. The model does the part that needs judgement, and the compiler does the part that needs to be certain. Neither is asked to do the other's job. Because the strict form is English, a person can read what the model wrote and see whether it is what they meant.

That step is not built here. What is built is the half that had to come first: a form of English precise enough to be worth translating into.

There is one more thing to say plainly. Most of this compiler was itself written by language models, under a person's direction, with one model reviewing another's work. That fits the thesis. The models were useful because a strict checker, a test suite of more than 130 tests, stood behind everything they wrote.

❦

Agents, and what a program means

The last chapter spoke of a model as a translator: a person says something loose, and the model writes the strict form. That is no longer the usual arrangement. A person now describes a task, and an agent, which is a language model working in a loop with tools, writes the program, runs it, reads what went wrong and tries again. The person writes very little. What is left to them is to read.

The reader is the narrow place

An agent can write a thousand lines in the time it takes a person to read fifty. Code that is approved without being understood has not been reviewed, and most people who are asked to approve an agent's work are being asked to read a notation that was made for writing in, and often one they do not know well. The honest choices are to trust the agent or to slow it down to the speed of its reader.

Two kinds of understanding

People say that a language model understands a sentence, and in a useful sense it does. It will nearly always pick the dragon you meant by “its hoard”. But its understanding is a likelihood. It cannot tell you which of its readings were certain and which were guesses, because to the model they are the same kind of thing.

The compiler's understanding is narrower, and of another kind. It knows what each word refers to and what kind of value each phrase has, and nothing more. It has no idea whether taxing dragons is wise. But within those limits it either has one reading, and can show it, or has two, and shows both. The Explain button in the playground prints, under each sentence, how that sentence was read. That printout is common ground: the person, the agent and the machine are all looking at the same statement of what the sentence means.

An agent needs both kinds. It needs judgement to get from an intention to a draft, and it needs something certain to tell it that the draft says one thing. A second model cannot be that something, because it is guessing as well.

What an agent needs from a language

  • Refusals it can act on. Every problem comes with its place, its reason and, where it is certain, the corrected sentence. The linter gives all of them at once, as data, with --lint --json. That is a loop an agent can run with nobody watching: write, check, mend, run.
  • No silent choices. The dangerous line in an agent's work is the one that is plausible and wrong. A language that picks a reading for you lets that line through. A language that refuses to pick turns some of those lines into errors before anything has run.
  • The intention kept in the program. “Never” and “for example” are sentences of the language, and they run. An agent that changes the program cannot drop one quietly. The change shows as an English sentence taken out, and that is a thing a reviewer notices.
  • A judge that is not a model. The same program means the same thing every time, so what passed yesterday still passes today.

What has been tried, and what has not

This repository is a small trial of the idea, in one direction only. Its example programs were written by a model working from the grammar. The first drafts were often refused: a reserved word used in a name, a preposition the language does not have, a variable given the name of one already in view. One program claimed that sorting eight numbers took thirteen swaps. The compiler ran it and answered that it took fourteen. Each was put right from the message alone.

What has not been tried is the claim that matters most. Nobody has measured whether a person reviewing an agent's work catches more mistakes in these sentences than in Python. There is a real danger on the other side, too: a sentence that reads easily may be read carelessly, and looking right is not the same as being right. The language is also wordier than code, which costs an agent time, and no model has been trained on it. And there is no agent here. There is only the language it would write in, and the checker that would stand behind it.
